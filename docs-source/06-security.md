# 6) الثوابت الأمنية

## غير قابلة للتفاوض

1. **لا أسرار خادمية في الواجهة.** الاستثناء الوحيد: `VITE_SUPABASE_URL` و`VITE_SUPABASE_ANON_KEY`.
2. **التنفيذ الخادمي فقط.** RLS ودوال `SECURITY DEFINER` هي المرجع؛ الواجهة تُخفي الأزرار فقط ولا تمنح صلاحية.
3. **الدلاء التخزينية خاصة دائمًا.** المتصفح يستلم روابط موقّعة صالحة 120 ثانية فقط.
4. **لا كتابة مباشرة** من `anon`/`authenticated` على أي جدول — كل الكتابة عبر دوال مخوّلة.
5. **السجلات الحرجة append-only.** التصحيح عبر `record_corrections` فقط.
6. **تحقق IMEI:** 15 رقمًا + Luhn، في الواجهة والخادم معًا.
7. **لا ادّعاء تتبّع موقع** من IMEI وحده.
8. **لا بيانات تجريبية ولا مدير ثابت.**
9. **لا إضعاف RLS/MFA/أذونات التخزين** لإنجاح الاختبارات.
10. **لا مشاركة مفتاح الخدمة السري أو كلمة مرور القاعدة في أي محادثة.**

## طبقات الحماية

| الطبقة | الآلية |
|---|---|
| المصادقة | Supabase Auth + TOTP، وفرض AAL2 عبر `private.require_aal2()` |
| التخويل | 7 أدوار × 31 صلاحية، يُتحقق منها بـ `public.require_permission()` |
| عزل الصفوف | RLS مفعّل ومفروض (`force`) على كل جدول |
| سلامة السجل | `audit_logs` بسلسلة تجزئة، ويتحقق منها `public.verify_audit_chain()` |
| البيانات الحساسة | نص مشفّر + تجزئة بحث، والوصول يتطلب صلاحية + مبرر ≥ 10 أحرف + تسجيل |
| تحديد المعدل | `public.op_rate_limit()` على نقاط الدخول الحساسة |
| آلة الحالات | انتقالات البلاغ محصورة في جدول `report_status_transitions` وحارس trigger |

## أعلام الجلسة (مزلق معروف)

تغيير حالة البلاغ والإحالة يستخدمان علمي جلسة مختلفين.
كل دالة **تُصفّر العلم الآخر** قبل تعيين علمها لمنع تسرّب الأعلام داخل الجلسة:

```sql
perform set_config('app.report_assignment', 'off', true);
perform set_config('app.report_status_transition', 'on', true);
```

يوجد اختبار انحدار يغطي تسلسل: إحالة ← متابعة ← تغيير حالة ← إحالة مرة أخرى.
